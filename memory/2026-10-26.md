## P0-1：命名空间内 async/Thread 解析失败（pebview 暴露）

- **现象**：`pebview/tests/hello.php` 跑出 `Call to undefined function Tphp\Pebview\Tphp\spawn()`，且在 FFI 回调里抛 → 直接 fatal。
- **根因**：parser 改写生成的是**相对名** `Tphp\spawn` / `Tphp\async`。`compile.c:resolve_func_name` 对"含 `\` 但不是以 `\` 开头"的名字会拼当前命名空间，且 **qualified 名不设 fallback**（只有裸名有 `ext=1` 回退），于是 `Tphp\Pebview` 下变成 `Tphp\Pebview\Tphp\spawn`。
- **修复**：`src/parse.c` 三处生成名加前导反斜杠——`\Tphp\spawn`(11) / `\Tphp\async`(11)。`resolve_func_name` 见 `\` 开头会剥掉并直接返回绝对名。
- **回归测试**：`tests/lang/test-async-in-namespace.php`（`namespace App;` 下调用形态 / 包装形态 / Thread thunk 三路）。
- **教训**：parser 生成的内置调用名一律写**绝对名**；`use function` 别名不参与 parser 改写路径，不能指望它兜底。

## P0-2：闭包内调用用户函数不执行（既有 bug，pebview 暴露）

- **现象**：pebview 点击无反应，关闭窗口后刷出一串 `read of undefined temporary (INIT_MCALL)` + `Argument #1 must be of type window, FFI\CData given`。
- **最小复现**（与 async 无关）：
  ```php
  function cmp(int $a, int $b): int { return $a <=> $b; }
  $arr = [3,1,2];
  usort($arr, function ($a,$b) { return cmp($a,$b); });   // read of undefined temporary (RETURN)
  ```
- **根因**：`tphp_vm_call_callable`（call_user_func / array_map / usort / FFI 回调 / Worker 回调的统一入口）用 thunk 循环执行闭包：
  ```c
  vm->x.frame = f;
  while (vm->x.frame == f) { ... }   // ← 闭包内调用户函数会建子帧 g，条件立刻为假
  ```
  子帧 g 挂在栈上**没被执行**，thunk 返回 `thunk_ret`（未设置）。帧链越积越深，后续指令读到的临时槽是 UNDEF。pebview 的 `$c_fn` 里 `self::ffi()->webview_return(...)` 正是"闭包内调方法"。
- **修复**：两处（方法帧 5125 / 普通闭包 5180）改用项目已有的 `run_frame_until_pop_deep(vm, f)`——跑到 f 真正弹出（`stop = f->prev` 先缓存防 UAF），子帧在同一循环内执行完。autoload 回调早就用的这个版本。
- **风险控制**：vm.c 注释警告"其余嵌套调用点保持旧式，改深会破坏析构/magic 时序（实测大面积 0xC0000005）"——所以**只改 `tphp_vm_call_callable` 这两处**，magic/析构路径的 2414/2478 保持旧式。
- **回归测试**：`tests/lang/test-callable-nested-call.php`（usort / call_user_func / array_map / 闭包内调方法）。
- **教训**：`while (vm->x.frame == f)` 这种"帧切换即退出"的写法只适用于**调用者自己会继续推进 VM** 的场景；同步调用（thunk）必须跑到帧弹出。

## Tphp\Thread 真线程化（用户拍板：Thread=真线程，Worker 内部化）

- **决策**：`Tphp\Thread` 从协程组改为**真线程池**（OS 线程并行）；`Tphp\TaskGroup` 保留为协程组；`Tphp\Worker` 保留公开名（既有测试/AsyncBinder 依赖），但不再是推荐 API。
- **为什么必须真线程**（pebview 卡 UI 的实验结论）：tphp 协程是单线程协作式调度，`webview_run` 是 C 阻塞调用占着 main fiber，协程只在 main 挂起时才能跑——而 main 挂起就是 UI 消息泵冻结。实测：bind 回调里 `async(task)` 不等待 → 回调返回后**一直饿死**（`[slow] end` 永不出现）；回调里 `usleep(100ms)` 主动挂起 → 协程能跑但 main fiber 冻结 = UI 卡死。**结论：UI 线程不能做任何会挂起/阻塞的事，重活必须真线程。**
- **实现**（ext/worker/worker.c）：
  - 新增 `Tphp\Thread` 类：`spawn(callable)`（一次性 Worker，入口 = 该 callable）/ `wait()`（按序收集结果）/ `detach()`（孤儿表）/ `count()`/`poll()`（非阻塞收割）。
  - **`tphp_sched_run(TVal *main_ret)`**：main 返回值传出（原来硬编码 NULL）——`tphp_vm_run_closure` 透传，`worker_thread` serialize 后 `wbox_put(to_parent)`。
  - **`cont_entry` 条件覆盖 `coro_result`**：原无条件 `= &c->result` 会覆盖外部接收槽（`main_ret` 拿不到值且所有权混乱）→ 改为 `if (!vm->x.coro_result)`。
  - **`tphp_run_shutdown_dtors` 加收尾锁**：多 Worker 几乎同时退出 → 并发收尾（共享 Program 类表/异常类克隆/常量表）→ mimalloc 报堆损坏。单 Worker 从不触发。
- **闭包跨线程序列化（T_CLOSURE）**：ext/serialize/serialize.c 加 'C' 格式 = Program 注册表 id + 函数索引 + 递归捕获；sr_val 重建 TClosure（gc_register）。**这是闭包能传给线程的前提**。
- **inc_prog 闭包解锁**：`worker_serialize_closure` 自动定位所属 Program（`tphp_vm_find_func_owner`），inc_prog 共享前对其 `tphp_prog_freeze`（幂等）。`WHandle.prog = owner`——**vendor/库文件里的闭包现在也能作为 Worker 入口**。
- **`tphp_prog_freeze` 改保存/恢复 `vm->prog`**：freeze 可能在活跃 VM 上调用，IC 预解析需要临时视图。
- **parser 注意**：`$g->spawn(add(1,2))` 走 `->spawn(EXPR)` 的 thunk 改写规则（通用），真线程收到的是无参 thunk 闭包，作为 Worker 入口正好。
- **测试迁移**：`test-async-taskgroup.php` / `test-tphp-async-syntax.php` 改用 `Tphp\TaskGroup`（协程组语义）；`test-serialize.php` 第 8 段从"closure 不可序列化 → not-cloneable"改为**往返验证**（闭包跨线程序列化是有意添加的新能力，EXPECT 随功能更新）。

## P1 根因确认：引用计数 bug（不是 mimalloc/GC 问题）

- **现象**：`Thread::spawn` 的一次性 Worker（无论 wait 还是 detach）在**进程退出**时 mimalloc 报 `corrupted free list entry (64b)` → fail-fast（0xC0000409）。功能输出全部正确。**常驻 Worker 不触发**。
- **诊断方法（关键突破）**：mimalloc 只报症状（"堆损坏"），不给根因。另建一份 **ASAN 构建**——**不定义 `TPHP_USE_MIMALLOC`**（走 CRT malloc，ASAN 才能接管），`clang -O1 -g -fsanitize=address` 编 src/+ext/，deps 对象复用主构建。ASAN 立刻给出**分配点/释放点/使用点**三条栈：
  ```
  use   tval_release (mem.c) ← frame_destroy (vm.c) ← op_return
  freed tarr_free (mem.c)    ← nm_thread_wait (worker.c)
  alloc tphp_obj_alloc (class.c) ← nm_thread_spawn (worker.c)
  ```
- **根因**：`nm_thread_spawn` 把 Worker 对象 `w`（alloc 后 rc=1）同时交给**跟踪数组 `a`** 和 **spawn 返回值**两个所有者，但 **`tarr_append` 按约定不做 addref**——数组接管调用方那份引用，调用方要自己继续持有必须**先 `tval_addref`**（约定见 `src/vm.c` `op_assign`，以及 vm.c:1527 注释 "the array takes its own ref"）。两处共用同一份引用计数 → `wait()` 释放数组时提前 free(w)，调用方帧随后再 release → **二次释放** → 写坏 mimalloc free list。**56 字节 TObj 正好落在报错里的 64b 尺寸类**，完全吻合。
- **修复**（ext/worker/worker.c）：
  1. `nm_thread_spawn`：`tarr_append` 前显式 `tval_addref(TV_OBJ(w))`——数组持一份、返回值持另一份，独立计数。
  2. `nm_thread_poll`：移出跟踪时补 `tval_release(&wv)`（原来只置 UNDEF = 漏释放）。
  3. `nm_worker_stop`：子线程已完成（state==done）时**也要 `uv_thread_join`**（原来直接 return = 漏 OS 线程资源）。
- **误诊清理**：`src/mem.c`/`src/value.h` 的 `gc_tid` 补丁（GCHead 记创建线程 id、跨线程 unregister 跳过摘链）**整体回退**——ASAN 证明堆损坏与 GC 注册表无关；且该补丁本身危险（跨线程对象永不摘链 → 链表留悬垂项）。回退后对照实验 10 轮全绿。
- **回归测试**（新增，纳入套件）：
  - `tests/async/test-thread-real.php`——wait 结果序 + **wait 后仍持有 spawn 返回值**（直接覆盖双所有者路径）+ count 归零。
  - `tests/async/test-thread-detach.php`——detach 立即返回 + 主线程与后台线程并发窗口。
  - 删掉临时文件 `tests/async/thread-real-manual.php`（不匹配 `test-*.php`，本就不会被 runner 收集）。
- **验证**：mimalloc 版连跑 15 轮零报错；ASAN 版 3 轮 + 40 线程 detach 压力全干净；全量 222/222。
- **教训**：**分配器报"堆损坏"时不要急着改 GC/分配器**——先用 ASAN 拿到三栈，定位到具体的所有权错误再动手。前两轮（GC 哨兵、gc_tid）都在治症状，且哨兵方案还引入了新故障（thread1/ser2 挂起）。
