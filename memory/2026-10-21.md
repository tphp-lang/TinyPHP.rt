# 2026-10-21 HTTPS 证书问题诊断与修复

## 症状
`tphp add https://github.com/tphp-lang/lib_rt` →
`PHP Warning: https: handshake with github.com failed: X509 - Certificate verification failed`。
但 example.com / curl.se 的 HTTPS 都正常。

## 诊断路径
1. net.c 握手失败路径只有 mbedtls_strerror 的笼统文案 → 先补诊断：
   `MBEDTLS_ERR_X509_CERT_VERIFY_FAILED` 时调 `mbedtls_ssl_get_verify_result` +
   `mbedtls_x509_crt_verify_info` 打印标志位（net.c tls_connect）。
2. 重建后标志位 = `0x8` = `MBEDTLS_X509_BADCERT_NOT_TRUSTED`（链不受信；
   非过期、非域名不符）。
3. `openssl s_client -connect github.com:443` 看真实链：
   - subject=CN=github.com
   - issuer=CN=SteamTools Certificate, O=BeyondDimension, C=CN ← **假证书**
   - 机器上装有加速器类工具（SteamTools/Watt Toolkit 家族）对 github.com
     做 TLS 中间人；其 CA 在 CurrentUser\Root 存储（2026-12-21 到期的那张有效）。
   - 浏览器/Go/Node 用系统信任库所以正常；tphp 内嵌 Mozilla 包不含该私有 CA
     → 拒绝握手是正确行为。

## 修复（用户拍板：并入 Windows 系统信任库）
- net.c `tls_cacert_load_win_store()`：`CertOpenSystemStoreW(L"ROOT")` 枚举，
  逐张 `mbedtls_x509_crt_parse_der` 追加进同一条信任链；单张失败忽略。
- 非 Windows `#ifdef _WIN32` 跳过；Linux CI 不受影响（build.sh 无改动）。
- build.cmd 两处 link 行加 `-lcrypt32`。
- 信任面 = 内嵌 Mozilla ∪ 系统 Root（union，与 Node 常见构建一致）。
- 验证：github.com/example.com/curl.se 全通；178 passed 0 failed；零警告。

## GitHub 仓库页 URL 支持（用户要求，当日演进）
- v1（上午）：`gh_repo_to_zip()` fetch 时改写，无 ref → HEAD.zip。
- **v2（下午，用户重新定义语义）**：
  - 无 ref → **查最新发布版并固化**：`gh_latest_ref()` 走 GitHub 匿名
    API（releases/latest → tag_name；失败回退 tags 列表本地 semver 排序；
    再失败回退默认分支 + stderr warning）。PLAN 原「不调 Release API」
    是 git 时代决策（git ls-remote 免费），无 git 下 API 是唯一可靠来源，
    已在 PLAN §7 注记推翻。
  - `:ref` 后缀（`url:v0.0.1` / `url:main`）+ CLI ref 参数共存，CLI 优先；
    `gh_split_url_ref` 只在 path 内最后一个 `/` 之后切 `:`（防协议/端口
    冒号），ref 限 [A-Za-z0-9._-]（含 `/` 的用 CLI 参数）。
  - mod.json 存**剥后缀的仓库 URL + ref 字段**（解析结果固化，install
    可复现）；同名 re-add = 重新解析刷新 ref。
- 实测：latest/:master/:v0.0.1/CLI ref 四形态 + install 回装全过。
- **踩坑三连**（bare URL 路径才触发）：
  1. `eff_ref = urlref`（栈数组空串）指针非 NULL 骗过 `!eff_ref` →
     恒走 HEAD.zip。空 ref 必须归一化为 NULL。
  2. `fetch_http` 每次 g_fetch 都 `run_source` 一个微型脚本；latest 解析
     + zip = 同进程两次 `tphp_vm_run` → 崩。根因：`sched_cleanup` 里
     `uv_loop_close(&g_loop)` 后 `g_loop_inited` 仍 true，二次
     `tphp_sched_run` 复用已关闭的 loop（0xC0000005）。修：cleanup 后
     复位 `g_loop_inited=false`；run_source 的内部类 init 也加了
     static once 守卫。
  3. 多次 fetch 依赖 run_source 可重入——此前所有 pkg 测试都是单 fetch，
     该路径从未被覆盖。

## V 0.5.2 vpm 对照（C:\Users\28249\Desktop\v-0.5.2）
- vpm 完全 **git clone**（`clone --recursive [--filter=blob:none]`，版本 =
  `--single-branch -b <tag>`），仓库 URL 天然支持；依赖用户机器有 git。
- 查询语法 `name@ver` / `url@ver`（rsplit_once('@')）；安装路径
  `~/.vmodules/<publisher>/<name>`；先 clone 到 tmp 再 mv；拒绝覆盖有本地
  改动的 git 目录。
- 双源：官方注册表服务器（`/api/packages/<name>` JSON → 真实 URL + 镜像
  选择）或直接外部 URL；v.mod dependencies 递归（可混注册名和 URL）。
- HTTPS：**Windows 走 vschannel（原生 SChannel）自动用系统证书库**，
  非 Windows 走 OpenSSL/mbedtls 配置 verify 路径——所以 V 从无内嵌 CA
  包问题。tphp 无 git 设计下用 zipball 改写等价实现了「仓库链接直装」。
