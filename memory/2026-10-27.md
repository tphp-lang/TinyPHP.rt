# 2026-10-27

## 链式 TMP-ADD codegen 崩溃：根因定位与修复

### 调查过程

1. **独立最小集复现**：`tools/ir_chainadd.c` 单独编译运行——single/chain 两模式都崩（0xC0000005）。重编 IR 对象（16 模块白名单 → `build/obj_ir/`）后仍崩，排除构建问题。

2. **阶段二分**（`tools/ir_bisect.c`）：逐步加 prologue/move/diamond/call/chain，锁定崩溃组合 = **move + diamond + slow CALL**（mode 14/30/31）。

3. **优化级别二分**：O0/O1 全过；**O2（含 SCCP）+ move + diamond + call 崩**。nomove 的 O2 也过。→ 崩溃 = SCCP 特有。

4. **节点级 diff**：pre-SCCP 图 CALL 操作数完整（7 参）；post-SCCP 第一个 CALL 的 `tb`（op8=37）被清零。use list 仍显示 CALL@66 用了 37，但操作数已为 0——说明清零未走正常 replace 路径。

5. **根因**：`ir_sccp_transform` 逐槽位扫描 `for (i=1; i<insns_count; i++)`。CALL 有 9 个输入 → `ir_insn_inputs_to_len(9)=3` 个连续 `ir_insn` 槽位。尾槽存的是 ops[] 载荷（op=241/37 等垃圾值），被当独立指令处理；对尾槽调 `ir_sccp_remove_insn` 时 `insn->opt=IR_NOP` 写到尾槽首字，即父 CALL 的 ops[8]——正好是 `tb` 参数。

6. **attempted fix（deps/ir/ir_sccp.c）**：transform 按指令长度前进 + TOP 路径跳过多槽位尾部。多次尝试均未完全修复（analyze 阶段也可能触雷；直接调 `ir_sccp` 与走 `ir_jit_compile` 行为不一致）。**放弃 patch deps/ir**，回退。

### 最终修复（workaround）

- `src/jit.c`：`ir_jit_compile(ctx, 2, ...)` → **`ir_jit_compile(ctx, 1, ...)`**——O1 跳过 SCCP，保留 CFG/GCM/RA/emit。O1 已验证链式 ADD 编译执行正确（s=60300）。
- `src/vm.c`：恢复急切编译——`n_ops <= TPHP_JIT_EAGER_MAX_OPS(96)` 首调即编，大函数仍走 hot threshold 127。

### 验证

- 链式 ADD：`TPHP_JIT=1` 下 `function sp($a,$b,$c){return $a+$b+$c;}` 首调编译，200 次循环结果正确。
- 循环内 if/else、嵌套循环：`jit_cfg_ok` 守卫仍生效；O1 下验证**仍崩**（独立于 SCCP 的 LOOP+MERGE codegen 缺陷），守卫保留。
- 全量测试：**223 passed / 0 failed**。

### 遗留（链式 ADD 相关）

- deps/ir `ir_sccp_transform` 多槽位 bug 未修（upstream）；O2/SCCP 恢复需先修此 bug。
- 循环内 if/else MERGE、嵌套循环：O1 下仍崩（钻石 MERGE 嵌 LOOP），`jit_cfg_ok` 守卫不可删。
- `tools/ir_bisect.c` 保留为独立复现/诊断工具。

## P0-2：direct-slot ABI（trampoline 免装箱）

### 问题

JIT→JIT 调用路径开销大：ALLOCA args → `tphp_jit_call` TLS 分配 + UNDEF 初始化 → callee prologue INT guard + args→slots 拷贝 + args 清零。fib 每次调用浪费 ~20 个内存操作。

### 方案（v1.2 direct-slot ABI）

1. **JitEntry 签名**：`(vm, slots, args_in, ret)` → `(vm, slots, ret)`——参数预写入 `slots[0..n]`
2. **去掉 prologue**：IR 不再生成 INT guard + args→slots 拷贝（JIT→JIT 调用方保证 INT；解释器路径在 C 侧 guard）
3. **直调路径**：`lower_call_finish` ALLOCA callee slots、参数直写、经 `tphp_jit_call_slots` 运行时查 `jit_entry` 后直调——无 TLS、无 UNDEF init for params
4. **解释器路径**（vm.c）：C 侧 guard 参数 INT + 拷贝 args→slots 后调 entry；guard 失败回落解释器

### 关键 bug

编译期直接嵌 `callee->jit_entry` 地址——递归函数编译时 entry 还是 NULL。改用 `tphp_jit_call_slots(vm, fn, slots, ret)` 在运行时查表。

### MEM2SSA 评估

启用 `IR_OPT_MEM2SSA` 反而更慢（32.9ms vs 24.2ms baseline）——slot 读写在封闭小函数里 IR 优化器已能处理，MEM2SSA 的 CFG/dominator 开销不划算。已回退。

### 结果

| 指标 | 前 | 后 |
|------|-----|-----|
| fib(28) | 20.8ms | **14.0ms** |
| vs PHP tracing JIT (~10.9ms) | ~1.9× | **~1.27×** |

全量测试 223/223 仍绿。

### 遗留

- arg 直传寄存器（Windows x64 前4参进 RCX/RDX/R8/R9）可进一步压缩调用开销，留待后续
- deps/ir SCCP 多槽位 bug、LOOP+MERGE codegen bug 未修（见上文）

### P0-3：字面量键 norm/hash 缓存（部分）

### 改动

1. **`GC_FLAG_NONNUM_KEY`**：`tstr_intern` 时检查是否为 canonical decimal int 键；非数字则打标记
2. **`tval_norm_key` 快路**：`T_STR` 带标记 → 直接 return true，跳过数字扫描
3. **`TSTR_HASH` 宏**：内联 `s->hash ? s->hash : tstr_hash(s)`，`key_hash` 改用

### 结果

kv-read 88.1ms → **84.9ms**（~4%）。收益有限原因：短字符串数字扫描本身便宜（"alpha" 第 2 字节即非数字）；剩余开销在函数调用链（rd→tarr_get→arr_find→key_eq）与 FFI 检查。

### 剩余机会

- opcode 级预存 hash（需 TOp 加字段或用 ic）——改动面大
- 变量键路径（roadmap 记 160ms vs 常量键 68.6ms 的 2.3×）——当前 bench 用常量键未覆盖
- FETCH_DIM_R 整路径内联/特化

## LOOP+MERGE codegen 崩溃根因（P0-1 剩余两形态）

### 调查

1. 临时放开 `jit_cfg_ok` 守卫 → 嵌套循环/循环内 if-else 均 `eligible=1, ir_check=1` 然后 0xC0000005
2. O0 过、O1 崩 → 问题在 GCM/RA/schedule 路径
3. 分阶段打点 → 崩在 `ir_schedule_blocks_bottom_up`
4. bitqueue 打点 → **bitset word0=0xffffffff（bit0 意外置位）**，pop 返回 b=0 → 访问未初始化 `cfg_blocks[0]` → 崩

### 根因

`deps/ir/ir_private.h` 对 64-bit 目标定义 `IR_BITSET_ONE = 1UL`。**Windows 是 LLP64**（`unsigned long` = 32 位），`1UL << 32` 为 UB，x86 移位模 32 变成 `1UL << 0` → 置位 bit0。block id ≥32（嵌套循环 CFG 有 43 块）时 bitset 被污染。

### 修复

1. `IR_BITSET_ONE = 1ULL`（全 64-bit 目标）
2. `ir_schedule_blocks_bottom_up` 的 edges 数组按 `cfg_blocks_count * 2 + 16` 分配（原 `cfg_edges_count/2` 在密集嵌套 CFG 下不够）

### 验证

- 嵌套循环 nl=135 ✓、循环 if/else li=160 ✓
- JIT 下 array-read 75.7ms（vs 解释器 90.1ms）、nested 6.5ms（vs 9.0ms）
- 223/223 全绿
